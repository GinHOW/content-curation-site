# 零、课程概述：最终要完成什么

## 0.1 课程定位

本课程以策展网站项目为实践对象，学习如何理解网站、组织内容、向 AI 描述任务、检查修改结果，并将项目可靠地发布到互联网。

AI Coding 意味着设计者的工作从直接执行视觉细节，进一步扩展为描述设计意图、组织项目系统、提出任务约束和判断最终结果。

## 0.2 核心任务

1. 看懂一个网站项目的大致结构和运行方式。
2. 把模糊的视觉、内容与交互想法转化为可执行任务。
3. 组织网站的数据、组件、素材与项目文件。
4. 限定 AI 的修改范围，通过预览、检查和版本记录验收结果。
5. 完成网站的协作、发布、优化与后续维护。

# 一、网站怎样工作

## 1.1 网站从一个文件夹开始

一个基础网站项目可以先被理解为一个有组织的文件夹，里面包含页面代码、样式、交互脚本、图片、字体、视频、内容数据和项目配置。浏览器中的网页，是浏览器读取这些文件、计算规则并将结果绘制到屏幕上的结果。

## 1.2 HTML、CSS、JavaScript 与素材

HTML 决定页面中有什么，相当于展品清单与空间结构；
CSS 决定这些内容怎样呈现，相当于视觉系统与陈列规则；
JavaScript 负责点击、切换、筛选和数据更新等行为，相当于展览中的互动机制；
图片、字体、音频和视频则是网站使用的具体素材。

## 1.3 浏览器怎样生成页面

浏览器的工作可以压缩成四个动作：

解析 HTML，建立页面结构；
解析 CSS，形成视觉规则；
执行 JavaScript，处理交互和内容变化；
计算布局并将页面绘制到屏幕上。

实际运行中，这些过程可能相互穿插。打开页面、载入新资源、改变窗口大小或执行交互时，浏览器都可能重新进行其中一部分计算。

### 从 HTML 到 DOM

浏览器读取 HTML 后，会把标签和文本转换成具有父子关系的对象，形成一棵 DOM 树（因为是父子层级的显示状态，所以是树）。HTML 是浏览器接收到的原始文档，DOM 是浏览器根据文档建立的、可以被 JavaScript 操作的当前页面结构。DOM 节点则是这棵树中的每一个对象，包括整个文档、HTML 元素和具体文本。

### 从结构到最终画面

浏览器根据 CSS 确定每个元素的样式，计算它们的尺寸和位置，再把结果绘制到屏幕上。JavaScript 可以在页面运行过程中增加、删除或修改 DOM 节点，浏览器随后重新计算并更新画面。

```diagram
HTML → DOM 结构
CSS → 样式规则
DOM + CSS → 布局与画面
JavaScript → 修改 DOM 和页面状态
```

## 1.4 网站怎样从本地电脑走向互联网

项目源文件、本地开发环境和线上网站不是同一个东西。网站上线的过程，是把面向开发者的本地源文件转换为浏览器可以接收的发布文件，再把它们交给网络服务器。

我们在编辑器中看到的网站项目，首先是供开发者阅读和修改的源文件。其中可能包含 HTML、CSS、JavaScript，也可能包含 Vue 组件、React 组件、Markdown、TypeScript 和各种配置文件。浏览器不一定能够直接运行所有源文件，因此网站从制作到上线通常会经过开发、构建和部署三个阶段。

### 开发：在本地持续修改和预览

开发阶段通常通过开发服务器读取项目，例如运行 npm run dev，再通过 localhost 地址访问网站。开发服务器会在代码变化时重新处理文件并刷新页面，帮助我们快速查看结果。
localhost 指向当前这台电脑，因此本地预览通常只有自己能够访问。它证明项目能够在当前开发环境中运行，暂时不能证明它能够成功构建和上线。

以这个仓库我们来做一些演示：

```resource
type: repository
title: Space Jam 1996 网站源码
url: https://github.com/wittenbrock/space-jam
preview: images/space-jam-github.jpg
```

（第八章我们会更详细讨论这两步）

### 构建：把源文件转换成发布文件
构建工具会读取组件、数据、样式和配置，把它们转换、组合和压缩成适合发布的 HTML、CSS、JavaScript 与素材文件。构建结果通常放在 dist、build 等输出目录中，具体名称由框架决定。

简单的 HTML 网站可以直接发布，不一定需要构建步骤。使用框架的项目通常需要先构建。构建也是上线前的一次检查：文件引用错误、依赖缺失和部分配置问题，可能在本地开发时没有暴露，却会导致构建失败。

### 部署：让发布结果可以被互联网访问
部署平台（云）会读取代码仓库，安装依赖，执行构建命令，再把构建结果放到能够响应互联网请求的服务器或全球节点上。部署成功后，平台会提供一个公开网址；连接域名之后，用户就可以通过正式域名访问。

如果是局域网访问，比如现在在这个学校里，我们直接通过局域网地址就可以访问。

## 1.5 前端与后端>>>浏览器端、服务器端与数据服务

人们经常用“前端”和“后端”粗略描述网站的两类工作，但它们不是网页中看得见和看不见的两层。

前端通常指下载到用户设备、在浏览器中运行的程序，其中既有可见界面，也有状态管理、数据处理和网络请求等不可见逻辑。后端通常指在服务器环境中运行的程序，负责处理请求、执行规则、检查权限和调用数据服务。数据库、对象存储和第三方接口是后端可能连接的服务，但不等同于后端本身。

“前端—后端”最初是一种方便描述开发分工的方式，并不是对网站系统的完整分类。现代网站至少还包含构建工具、数据库、对象存储、身份认证、CMS、CDN、部署平台和第三方接口。Cloudflare Workers 这类边缘计算甚至运行在用户与传统服务器之间，很难简单塞进传统的前后两端。

因此，分析网站时，可以先选择一个具体功能，观察它从用户操作到结果出现经历了什么。沿着这条过程，可以继续确认代码分别在哪里运行、数据保存在哪里，以及请求经过了哪些服务。把一次功能的完整过程画出来，就得到了网站的一条基本运行链路。

> [!example] 举例｜提交展览预约
> 浏览器收集表单内容并发出请求，服务器检查名额和用户信息，数据库保存预约记录，服务器返回处理结果，浏览器再更新页面。

分析一项网站功能时，还要判断结果是在构建阶段提前生成，还是在用户请求发生时即时计算。前者可以直接作为文件交付，后者需要某种服务端计算能力，但这种能力可以来自 Workers 等托管平台，不一定需要单独购买云服务器。


> [!example] 举例｜课程网站的两种生成方式
> 课程介绍、章节目录和教学资料可以在发布时提前生成，用户访问时直接读取已经生成的页面文件。如果网站进一步提供学生登录、作业提交、学习进度记录或评论功能，就需要在用户操作发生时检查身份、读取或写入数据，并返回相应结果。同一个课程网站因此可以同时包含提前生成的内容和需要即时计算的功能。

# 二、网站怎样被组织

之所以需要讨论网站的组织方式，是因为 AI 可以快速生成一个看起来可用的页面，却未必会主动建立清晰的数据结构、组件边界和内容关系。项目一旦增加页面、内容或功能，缺乏组织的代码就容易出现重复、修改失控和难以维护等问题。

这一章将关注网站中的内容、页面和工具怎样形成一个可以持续扩展的系统。我们会先分清数据、组件和页面，再确定内容之间的关系与访问路径，随后判断项目需要多少交互和状态，最后选择相应的框架、素材管理方式和项目配置。

## 2.1 从页面到系统

当网站从一张页面扩展为大量内容、多个页面和一组重复规则时，逐页手工维护 HTML、CSS 和 JavaScript 会越来越困难。网站设计因此会从单个页面的视觉安排，进一步发展为内容、数据、组件、状态和技术栈的系统设计。

> [!example] 举例｜从 6 件作品到 300 件作品
> 一个线上展览最初只有 6 件作品，可以直接在一个 HTML 文件中逐项写入标题、作者、图片和介绍。当作品增加到 300 件，并且每件作品都需要详情页时，继续手工复制页面会产生大量重复代码。如果要统一修改图片比例、作者信息的位置或“查看详情”的文字，就必须修改几百处内容，也容易出现遗漏。
>
> 更合理的方式是把作品名称、作者、年份和图片地址整理成数据，建立统一的“作品卡片”和“作品详情”组件，再由程序根据数据自动生成页面。用户当前选择的年份、分类和排序方式则作为状态保存。此时设计者处理的已经不只是一张页面，还包括内容怎样存储、组件怎样复用、状态怎样变化，以及使用什么工具组织和发布整个系统。

## 2.2 数据、组件与页面

为了让网站便于扩展和统一修改，可以把它粗略拆成数据、组件和页面三个层次。数据是网站需要展示的具体内容；组件是一组可以重复使用的结构、样式和交互规则；页面则根据特定的访问目的，将数据放入组件，并把多个组件组织成完整界面。

> [!example] 举例｜作品数据、卡片与列表页
> 作品名称、作者、年份、图片地址和介绍属于数据；规定图片比例、文字层级和点击行为的“作品卡片”属于组件；把筛选栏、作品卡片和分页组织起来，就形成了作品列表页面。同一份作品数据还可以进入搜索结果、作者主页和首页推荐等不同位置。

分开这三个层次，是为了判断一次修改会影响哪里。修改一条数据，只会改变某件作品的内容；修改作品卡片组件，会影响所有使用该组件的位置；调整页面，则会改变多个组件在某个访问场景中的组合方式。对于 Vibe Coding，这种区分也能帮助我们准确告诉 AI：这次需要修改具体内容、公共规则，还是某个页面的结构。

数据、组件和页面是理解网站组织方式的基础模型，并非互不重叠的技术边界。在 React、Vue 等框架中，完整页面通常也会作为一个较大的组件实现；这里的区分强调的是它们在系统中承担的不同职责。

## 2.3 网站常见的界面组件

网站虽然有很多设计风格，但长期使用下来，已经形成了一套常见的界面组件。认识这些名称，可以帮助我们分析参考网站、组织自己的页面，也能让我们更准确地告诉 AI 要生成或修改什么。

Header 是网站顶部的全局区域，通常包含网站名称、Logo、主导航、搜索、语言切换或登录入口。Navigation 指导航本身，它可以放在 Header 中，也可能表现为侧边栏、目录或手机端菜单。设计 Header 时需要考虑当前页面提示、菜单层级，以及滚动后是否固定在屏幕顶部。

Hero 是首页或重要页面最先出现的主视觉区域，通常使用较大的标题、图片、视频和简短说明，有时还会提供一个主要操作按钮。Hero 的任务是快速建立页面主题和视觉印象。它并非每个网站都必须拥有，档案、工具和信息密集型页面可能更适合直接进入内容。

页面中部通常由多个 Section 组成，每个 Section 负责一个相对完整的内容主题。Card 用于重复展示同一类内容，例如作品卡片、课程卡片和文章卡片；多个 Card 可以进一步组成 List、Grid、Gallery 或 Carousel。Button 和 Link 引导用户执行操作或前往其他页面，Tag、Badge 和 Metadata 则用来补充分类、状态、作者和时间等信息。

具有交互的页面还会使用 Form、Tabs、Accordion、Dropdown、Modal 和 Drawer。Form 用于搜索、登录和提交信息；Tabs 在几组并列内容之间切换；Accordion 展开和收起补充内容；Modal 会在当前页面上方打开一个临时窗口；Drawer 通常从屏幕边缘滑出，手机导航就是常见例子。选择这些组件时，要根据内容关系和操作目的判断，避免为了显得丰富而加入没有必要的交互。

Footer 位于网站底部，通常包含版权信息、联系方式、辅助导航、社交媒体和隐私条款。它也可以承担网站最后一次信息总结或行动引导。对于内容较多的网站，Footer 还是全局导航的补充入口。

组件之间可以继续嵌套。一个首页可以由 Header、Main 和 Footer 组成；Main 中包含 Hero、作品推荐和课程介绍等 Section；作品推荐中又包含多个作品 Card；Card 内部还可以包含 Image、Tag、Title 和 Link。通过这种层层组合，复杂页面可以被拆解成一组职责比较清楚的部分。

这些名称大多是设计和开发中的通用称呼，不完全等同于 HTML 标签。HTML 中确实存在 `<header>`、`<nav>`、`<main>` 和 `<footer>` 等语义标签，但并不存在标准的 `<hero>` 或 `<card>` 标签。Hero 和 Card 通常由多个 HTML 元素组合实现，再通过 CSS 和 JavaScript获得具体的视觉与交互效果。

认识组件名称只是建立共同语言。向 AI 提出任务时，还要继续说明组件中包含什么内容、怎样排列、怎样交互，以及在手机上如何变化。例如，“添加一个 Hero”仍然比较模糊，可以进一步描述为：

```prompt
在首页导航下方添加一个 Hero 区域，左侧显示课程标题、两行介绍和“查看课程”按钮，右侧使用课程主视觉图片。电脑端采用左右两栏，手机端改为上下排列，图片移动到文字下方。
```

## 2.4 信息架构与导航

理解数据、组件和页面之后，还要回答这些内容怎样形成一个整体。

在编写页面之前，应先盘点网站有哪些内容类型，它们之间有什么关系，用户会带着什么目的进入网站，以及需要经过哪些路径才能找到目标内容。这个过程就是信息架构设计。

> [!example] 举例｜线上展览的信息架构
> 展览、艺术家、作品和文章是四种不同的内容类型。一件作品可能属于一个展览，也可能与一位艺术家和多篇文章相关。梳理这些关系之后，才能决定作品数据需要哪些字段，应该建立哪些列表页与详情页，以及导航中需要出现“展览”“艺术家”还是“作品”等入口。

信息架构描述内容怎样分类和关联；页面结构决定某一页先出现什么、后出现什么；导航则把重要内容和访问路径呈现给用户。课堂上可以先用内容关系图回答“网站里有什么”，再用站点地图回答“有哪些页面”，最后用用户路径回答“人怎样到达目标”。


## 2.5 网页与 Web 应用

判断用户主要是在浏览内容，还是持续操作一个系统。这个判断会影响项目需要管理多少状态、是否需要账户和数据库，以及应该选择多复杂的技术方案。

传统内容型网页主要帮助用户获取信息，核心组织单位通常是页面，例如展览介绍、作品档案和专题文章。Web 应用允许用户持续操作同一个系统，例如编辑资料、收藏作品、提交预约或协同管理内容。此时核心问题逐渐转向应用状态，即系统当前保存了什么、用户正在进行什么操作，以及界面应该怎样响应变化。

> [!example] 举例｜Figma 作为 Web 应用
> 用户进入一个设计文件后，会持续进行选择图层、修改属性、移动对象、添加评论和多人协作等操作。系统需要不断记录当前选中的对象、画布状态、文件内容、修改历史和协作者变化，并让界面及时响应。此时设计重点已经从“展示哪些页面”转向“系统需要记住哪些状态，以及用户操作怎样改变这些状态”。

状态可以先理解为“系统此刻需要记住的信息”。筛选器当前选择的年份、轮播图正在显示的图片，属于界面状态；某个用户收藏了哪些作品、预约是否提交成功，属于需要跨页面或长期保存的业务状态。前一种状态通常可以留在浏览器中，后一种状态往往需要后端和数据库参与。

网页和 Web 应用之间没有绝对分界。同一个策展网站的大部分内容可以提前生成并直接浏览，同时加入搜索、收藏和预约等应用功能。区分二者，是为了根据实际任务判断状态和交互的复杂度。

## 2.6 前端框架 React、Vue 与 Astro等

当页面、组件、数据和状态不断增加时，需要一套稳定的方式管理它们之间的关系。前端框架会提供组件组织、数据传递、状态更新、页面生成和开发构建等能力，使同一种规则能够在整个项目中重复使用。框架最终仍然要把结果转换为浏览器能够理解的 HTML、CSS 和 JavaScript。

React 以组件作为组织用户界面的核心单位，适合需要组合大量界面模块和复杂交互的项目。Vue 建立在 HTML、CSS 和 JavaScript 之上，提供声明式、组件化和渐进式的使用方式，可以从局部交互逐步扩展到完整应用。Astro 更强调以内容和页面为中心，默认将大部分界面生成静态 HTML，只为需要交互的局部加载 JavaScript，适合内容占主体、局部具有交互的项目。

框架的选择应当从项目特征出发：内容页面占多少，用户操作是否复杂，需要保存多少状态，团队熟悉什么工具，网站怎样生成和发布。课程会选择一种默认技术栈完成实践，其他框架用于理解不同的组织思路，不要求同时掌握。框架可以帮助实现系统，但不会自动替代数据结构、组件边界和页面关系等设计决策。

## 2.7 图片、字体与内容数据

网站除了代码，还包含图片、字体、音频、视频、文本和结构化数据。它们需要按照稳定的目录、命名和元数据规则管理，否则项目扩大之后容易出现重复文件、失效链接、来源不明和难以替换等问题。

首先要区分素材文件与内容数据。图片、字体、音频和视频是网站调用的文件资源；作品标题、作者、年份、分类和图片地址则是描述内容的数据。一张作品图片可以保存在项目目录或对象存储中，同时由一条作品数据记录它的地址、说明文字、版权来源和替代文本。

接下来要判断内容在什么阶段进入网站。很少变化的图标和界面字体可以随项目一起发布；由设计者维护的文章可以保存在 Markdown 文件中；需要编辑团队频繁更新的内容可以放在 CMS 或在线表格中；需要查询、关联或由用户持续写入的数据则可能进入数据库。

## 2.8 技术栈、配置文件与依赖

一个网站项目通常需要多种技术共同完成。负责页面和组件的框架、负责转换代码的构建工具、负责保存内容的数据方案，以及负责网站上线的部署平台，共同构成这个项目的技术栈。技术栈描述的是项目选择了哪些技术、它们分别解决什么问题，以及它们怎样连接起来。

> [!example] 举例｜两套不同的技术栈
> 一个策展网站可以使用 Astro 组织页面和组件，使用 Markdown 保存文章，使用 CSS 控制视觉样式，使用少量 React 制作交互组件，最后发布到 Cloudflare。这些相互配合的技术形成了一套技术栈。另一个项目可能使用 Vue 构建界面、数据库保存用户数据，再通过 Vercel 发布，它会形成另一套技术栈。

技术栈确定之后，配置文件负责记录这些工具怎样开发、构建和发布，依赖则为项目提供可以直接调用的外部代码。它们通常不直接出现在页面上，却会决定项目能否正常安装、运行和部署。

例如，`package.json` 会记录项目脚本和主要依赖，锁定文件会保存实际安装的依赖版本，框架配置文件会规定构建方式、插件和输出结果，环境变量文件则为不同运行环境提供地址、标识和密钥等配置。具体文件名称会随技术栈变化，学习重点是先判断一个文件承担什么职责，再决定是否修改。

依赖是项目为了完成某项功能而引入的外部代码包，可以帮助我们复用已有成果，减少重复开发，例如使用现成工具处理日期、图标或动画。Vue 从功能上看是一套前端框架；当一个项目安装并使用 Vue 时，Vue 同时也是这个项目的一项依赖。

每增加一个依赖，也会增加版本兼容、代码体积、安全更新和长期维护成本。让 AI 安装新依赖之前，需要先确认它要解决什么问题、现有项目是否已经具备相同能力、依赖是否仍在维护，以及它会修改哪些配置和锁定文件。

让 AI 修改项目前，还应先识别项目已有的技术栈。随意引入新的框架、构建工具或功能相似的依赖，可能使同一个项目出现多套重复方案，增加冲突和维护成本。修改配置和依赖之后，至少需要重新构建或运行项目，并检查相关文件的修改差异。

可以把三者的关系概括为：技术栈说明项目整体选择了哪些技术，配置文件规定这些技术怎样连接和运行，依赖则是项目具体调用的外部代码包。

# 三、Vibe Coding：怎样与 AI 一起工作

## 3.1 AI Coding 工作台的各种界面

在 AI Coding 出现之前，IDE 和代码编辑器是开发者最主要的工作环境。它们围绕代码与文件组织工作，将项目目录、代码编辑、运行调试、版本管理和插件系统集中在一个界面中。开发者负责理解项目、寻找文件、编写代码并检查结果，工具主要提供编辑和辅助能力。

AI 最初作为一种辅助功能进入 IDE，例如代码补全、解释代码、生成局部片段和提供修改建议。此时工作的核心仍然是代码，AI 帮助开发者更快地完成某一步操作。比如 很出名的Cursor。

随着模型能够搜索项目、修改多个文件、运行命令和检查结果，AI 开始从代码助手转向任务智能体。用户可以先描述目标，让智能体围绕任务组织上下文、调用工具并持续执行，再通过对话、文件差异和运行结果进行检查和修正。由此出现了以任务和对话为中心的 AI Coding 工作台。

另外一种原始的操作方式，现在也在复兴——CLI 则提供了另一种操作入口。它直接连接项目目录、系统命令和开发工具，适合运行、构建、测试、版本管理和自动化。现代 AI Coding 产品通常会同时进入 IDE、CLI、桌面端和云端，因此这些形态之间会相互结合，而非彼此替代。

## 3.2 基本协作循环

AI Coding 在交互这件事上，本身没有什么技术含量——主要就是对话。以前学习 AI（被剥夺了简称的 Adobe Illustrator），或者学习 Pr，首先要认识各种面板、工具和快捷键。现在打开 AI Coding 工具，直接用自然语言描述想做什么，就可以开始工作。

但会说话，不代表就会和 AI 一起完成项目。就网站来讲，你只说一句“帮我做一个课程网站”，AI 确实可能很快做出一个能看的结果，也可能顺手写出一个三千行的大文件，把内容、样式和交互全部塞在一起。它还可能为了修改一个按钮重做整套样式，遇到报错就不断安装新依赖，重复制造功能相同的组件，或者在没有实际检查的情况下宣布任务已经完成。网站暂时能运行，等到增加页面、统一样式、适配手机或者正式发布时，各种问题就会一起出现。

所以我们和 AI 在网站上的协作，如果是在现有项目上做修改，要让 AI 先阅读现有项目，弄清楚技术栈、目录结构和已经存在的组件，不要一上来就新建一套东西。其次，是明确这次要达到什么结果、哪些内容不能动、允许修改哪些文件，以及怎样才算完成。如果遇到超出范围的选择，先停下来询问。

而且不要一口气就冲去改特别多东西，每次只推进一个能够预览和检查的结果。不要一口气同时重做页面、替换框架、安装依赖和调整数据结构，否则出现问题之后很难知道是哪一步造成的。

当 AI 执行完之后，一方面要打开网站，检查内容、视觉、交互和不同屏幕尺寸；另一方面要查看文件差异、终端输出和依赖变化。页面看起来正常，不代表项目结构没有被破坏；AI 说已经完成，也不代表它真的运行和测试过。结果符合预期就保存一个可靠版本；存在局部问题就根据证据继续修正；方向已经偏离就及时回退，不要让 AI 在错误方案上不断打补丁。

这个过程可以压缩成一个反复执行的循环：

```diagram
理解项目 → 明确目标与边界 → 确认方案 → 小步执行
    ↑                                      ↓
验收或回退 ← 局部修正 ← 检查文件差异 ← 预览与运行验证
```


## 3.3 把设计意图转化为任务

另外我始终认为艺术设计师在 AI 时代有很大一波审美红利可以吃。

以前把一个设计想法变成真正可以访问的网站，中间隔着代码、框架、浏览器和部署等一整套技术门槛。设计师可能知道自己想要什么，却未必能够亲手把它做出来。AI 正在压缩这段距离：你可以直接描述意图、观察结果、继续修改，很多过去需要和开发者来回沟通的事情，现在可以自己先做出原型。

当“能不能做出来”逐渐变得容易，“究竟应该做成什么样”反而更加重要。AI 很擅长快速生成一个看起来完整、基本正确的方案，但它的默认结果经常是安全、平均和似曾相识的。它可以生成十种方案，却不知道哪一种真正适合这个项目。设计师对比例、节奏、字体、图像、内容层级和文化语境的判断，就会成为区分结果的关键。（顺便说一句，特别希望加一个左边线作为卡片是一个很 AI 的视觉）

但审美不能只停留在“我觉得不对”或者“再高级一点”。如果不能把这种感觉转化成 AI 可以理解和执行的要求，审美优势就很难真正进入项目。我们需要进一步说明哪里不对、为什么不对、哪些关系需要保留，以及修改之后应该出现什么可以观察的变化。

对学平面设计的大家来说，网格、版式、字体和图形方面的训练，以及从参考图中提炼视觉规律、把它们组织成一套设计系统的能力，都会成为进入 Web 和应用设计时的优势。

所以，AI 时代的设计能力不只是产生想法，还要把审美判断转化为可以执行和检查的结构、规则、约束与验收标准。这个转化过程本身就是设计的策略化和结构化。落实到与 AI 的协作中，一个相对完整的任务描述应当包含项目背景、修改目标、已有素材、限制条件、具体操作、验收标准，以及结果不符合预期时的恢复方式。（后面我们再介绍下 Design.md)

## 3.4 Agent 的工作模式与任务控制

Agent 工具不只回答问题，还可以围绕任务读取文件、使用工具、修改项目和验证结果。任务复杂度不同，需要采用的工作方式也不同：需求尚未明确时先进行规划；目标明确但工作量较大时持续追踪目标；多个部分可以独立处理时再考虑分配给子智能体。

### Plan 模式：先调查和规划

Plan 模式适合复杂、模糊或者影响范围较大的任务。Agent 会先收集项目上下文、识别需要确认的问题，并把目标拆成可以执行和验证的步骤。它的阶段性成果是一份执行方案，重点是先确定“准备怎样做”，再进入实际修改。

比如在 Codex 中输入 `/plan` 可以切换到 Plan 模式，也可以直接在命令后写入规划任务；桌面端还可以使用 `Shift + Tab` 切换。规划请求仍然需要提供目标、相关文件、限制条件和验收标准，

拿到计划之后，需要检查它是否理解了项目现状，是否遗漏内容、响应式、数据和发布等环节，以及每一步是否有可以观察的结果。计划仍然可以继续讨论和调整，确认后再让 Agent 按步骤执行。

### Goal 模式：持续推进到明确终点

Goal 模式适合超出一次对话、需要多轮执行和验证的工作。它会把一个目标持续附着在当前任务中，使 Agent 能够按照检查点推进，直到达到预先写明的停止条件。适合网站迁移、较大范围的重构、持续调试和完整原型制作，不适合一组彼此无关的零散事项。

在 Codex 中输入 `/goal <目标>` 可以建立目标，输入 `/goal` 查看当前状态；`/goal edit` 用于修改目标，`/goal pause` 和 `/goal resume` 用于暂停与继续，`/goal clear` 用于移除目标。一个有效目标需要说明完成什么、不能改什么、怎样验证以及何时停止，例如：

```prompt
/goal 完成作品档案网站的移动端适配。保留桌面端布局和现有内容数据；逐页检查首页、列表页和详情页；在三个规定宽度下没有横向滚动且导航可用时停止。
```

Goal 模式的关键是提供可验证的终点。“把网站做好”无法判断何时完成，“所有指定页面通过移动端检查并保留桌面端效果”才构成停止条件。执行过程中可以要求 Agent 汇报当前检查点、已经验证的结果、剩余工作和阻塞原因。

### Subagent：把独立任务分给子智能体

主 Agent 负责理解总体目标、组织工作和汇总结果，子智能体负责边界清晰的局部任务。它适合并行进行项目结构调查、资料整理、测试、日志分析或从不同角度审查同一结果。多个智能体同时修改相同文件容易产生冲突，因此并行工作应优先用于阅读和分析；确实需要写文件时，要先划分互不重叠的修改范围。

在 Codex 中可以直接说明怎样分工以及希望返回什么结果，例如：

```prompt
使用三个子智能体并行检查这个网站，分别负责移动端布局、内容与链接、性能与可访问性；等待全部完成后，按优先级汇总问题，不要修改文件。
```

桌面端可以查看各个子智能体任务，CLI 中可以使用 `/agent` 查看并切换线程。每个子智能体都会独立消耗上下文和 Token，因此任务简单或无法并行时，使用一个 Agent 更合适。

### 三种方式怎样配合

简单且范围清楚的任务可以直接交给 Agent 执行；需求复杂或存在重要选择时，先使用 Plan 模式形成方案；方案确认后，如果实施过程需要跨多轮持续推进，再将它设为 Goal；其中可以独立调查或检查的部分，可以交给 Subagent 并行完成。它们解决的是规划、持续执行和任务分工三个不同问题。

## 3.5 Skills 与 MCP：让 Agent 掌握方法并连接工具


```resource

title: Agent Skill 从使用到原理，一次讲清
url: https://www.bilibili.com/video/BV1cGigBQE6n/
```


Agent 能够读取文件、运行命令和修改项目，但它不会天生掌握每个领域的最佳工作方法，也不会自动拥有 Figma、浏览器、资料库和其他外部系统的访问权。Skills 和 MCP 是两种不同的能力扩展：前者把工作方法交给 Agent，后者把外部工具接入 Agent。

### Skill：可以复用的工作方法

Skill 可以先理解为一份给 Agent 使用的专业操作手册。它会说明这项能力适合什么任务、应该按什么步骤执行、需要检查哪些结果，以及哪些风险需要暂停确认。一个 Skill 通常以 `SKILL.md` 为核心，还可以带上脚本、参考资料和模板等资源。

例如，“检查网站性能”不只是打开 Lighthouse 看一个分数。一个网页性能 Skill 可以规定 Agent 先记录真实加载过程，再检查图片、字体、JavaScript、网络请求和布局跳动，按影响大小提出修改，最后重新测量。以后再检查其他网站时，同一套流程就可以继续复用。

在 Codex 中，可以通过 `$Skill名称` 明确指定一个 Skill；当任务与 Skill 的用途明显匹配时，Agent 也可以自动选择它。Agent 初始只需要看到 Skill 的名称和简介，真正需要使用时再读取完整说明，这样可以减少不必要的上下文消耗。

### MCP：让 Agent 连接外部工具

MCP 的全称是 Model Context Protocol，可以理解为 AI 连接外部工具和上下文的一套通用接口。MCP 本身不是 Figma、GitHub 或浏览器，它规定这些服务怎样把可用操作告诉 Agent，以及 Agent 怎样发出调用请求并取回结果。

没有 MCP 时，我们可能需要将 Figma 标注、网页错误或在线资料手工复制到对话中。连接相应的 MCP 服务后，Agent 可以在权限范围内读取设计文件、检查浏览器页面、查询资料，或调用服务提供的其他操作。MCP 服务可以在本地电脑上运行，也可以通过网络连接远程服务。

连接 MCP 不等于把整个账户无限制地交给 AI。Agent 能做什么，取决于 MCP 服务实际提供了哪些工具、当前账户授予了什么权限，以及工具调用是否需要人工批准。连接外部服务时，仍然要检查数据范围、账户权限和写入操作。

### Skills 和 MCP 怎样配合

```diagram
提示词     → 说明这一次要做什么
AGENTS.md  → 规定这个项目长期遵守什么
Skill      → 提供完成一类任务的可复用方法
MCP        → 提供可以读取或操作的外部工具
```

> [!example] 举例｜从 Figma 设计到网站代码
> Figma MCP 让 Agent 能够读取设计文件中的页面、组件和视觉参数；设计转代码 Skill 则规定它应该按什么顺序理解设计、如何复用现有组件，以及完成后怎样检查还原度。只有 MCP，Agent 虽然拿到了工具，执行方法可能仍然不稳定；只有 Skill，Agent 知道应该怎样做，却可能无法直接读取外部设计。

基础课程不要求大家立即编写 Skill 或搭建 MCP 服务。这里先建立一个判断：如果想让 Agent 稳定重复一套工作流程，可以寻找或制作 Skill；如果想让它进入某个外部工具读取数据或执行操作，就需要相应的 MCP 连接。课堂上只做使用演示，先确保大家掌握 Agent 的基本工作模式、项目上下文和验收流程。


## 3.6 从提问到共同解决问题

当 AI 缺少上下文时，先让它阅读相关文件、复述现状并提出计划；当任务过大时，拆成彼此可验证的小任务；当结果不符合预期时，指出具体差异和证据，再要求局部修正。


# 四、项目约束与上下文管理

## 4.1 Token、成本与上下文

Token 可以先理解为 AI 读取和生成信息时使用的计量单位。我们输入的任务描述、提供的项目文件、保留的对话历史，以及 AI 返回的内容，都会占用 Token。与 AI 协作的成本因此不只取决于聊了多少轮，也取决于每一轮需要读取多少上下文、生成多少内容。不同产品会把这种消耗体现为 API 费用、使用额度、响应速度或任务限制。

上下文意味着 AI 在当前任务中能够看到并用于判断的信息，包括任务描述、对话历史、项目说明、相关文件、图片、终端输出和工具返回结果。AI 不会自动知道整个项目，也不会永久记住所有讨论；没有进入当前上下文的信息，它通常无法据此工作。

上下文越长并不必然意味着结果越好，重复内容、无关文件和过长对话会增加成本，也可能干扰判断。需要学习怎样选择相关文件、压缩背景和保存阶段性结论。

此外，在实际的 Agent 使用中过长的上下文（超多轮对话），也会导致输出速度变慢。

## 4.2 Markdown 与项目说明文件

Markdown 是一种使用纯文本符号组织内容的轻量标记格式，文件通常以 .md 结尾。在 AI 工具中，Markdown 已经成为最常见的文本组织格式之一。它既能保存自然语言，又能通过标题、列表和代码块建立清楚的结构，方便 AI 定位具体章节，也方便人阅读和检查修改。与 Word 等格式相比，Markdown 更轻量，便于搜索、复制、版本管理和长期维护。

Markdown 使用 # 表示标题、- 表示列表、[]() 插入链接，也可以记录图片、引用、表格和代码。即使没有经过渲染，原始文本仍然能够直接阅读；经过 GitHub、Obsidian 等工具渲染后，则会显示为层级清楚、具有基本排版的文档。

在网站项目中，Markdown 可以用来记录项目说明、设计规范、任务计划和验收结果，也可以直接保存课程文章、作品介绍等网站内容。不同文件应承担清晰而稳定的职责，避免把项目说明、长期规则、临时任务和内容资料全部堆积在同一个文档中。

## 4.3 README.md

README.md 面向项目参与者，说明项目是什么、怎样运行、目录如何组织，以及开发和发布需要哪些基本条件，也可以帮助 AI 快速建立对项目的基本认识。

一般来讲它回答几个最基础的问题：这是什么项目，主要解决什么问题，使用了哪些技术，重要文件放在哪里，以及怎样在本地运行和查看结果。

## 4.4 AGENTS.md

大家应该都听过 Prompt，也就是提示词。我们通常在当前对话中写提示词，告诉 AI“这一次要做什么”。但有些要求并不只属于某一次任务，例如项目使用什么技术、哪些文件不能修改、是否允许安装依赖、代码应该怎样命名，以及完成后必须执行哪些检查。如果每次对话都重新说一遍，会很麻烦，也容易遗漏。

AGENTS.md 可以先理解为写在项目里的长期提示词。普通 Prompt 像这一次交代的任务，AGENTS.md 则像贴在工作室墙上的工作守则：只要进入这个项目，AI 就应该先阅读并遵守。在 Codex 中，这个文件会在开始工作前被读取，并作为项目指令加入当前任务。

## 4.5 DESIGN.md

DESIGN.md 也是提示词，这个概念主要由谷歌的 Stitch 项目明确提出,专门约束 AI 的设计。它把设计师头脑中的视觉判断整理成文字规则，记录项目的视觉方向、信息层级、颜色、字体、间距、组件状态和响应式行为，帮助 AI 在多轮修改和不同页面之间保持一致。

用于记录项目的视觉方向、信息层级、颜色、字体、间距、组件状态和响应式规则。它帮助设计意图在多轮修改中保持一致。

# 五、检查、修正与恢复

## 5.1 控制修改范围

让 AI 开始工作之前，应当明确哪些文件可以修改、哪些内容需要保留、是否允许安装依赖，以及什么情况必须先询问。优先采用小范围、可预览和可撤销的修改。

很多时候AI直接开始改，如果是简单工作没什么问题，但如果是复杂的任务，还是建议先做计划。

## 5.2 执行过程中终止或插话补充
现在一些 Agent 允许我们在任务执行过程中继续发送消息，也就是中途“插话”。如果整体方向没有问题，只是发现它漏掉了某个条件，可以直接补充，例如：“导航结构保持不变，只调整正文区域”“不要安装新的依赖”“先完成当前页面，不要继续修改其他页面”。现在的 Codex 工作流也强调在任务执行中继续引导、审查和调整。

不过，插话并不等于实时遥控。Agent 可能正在执行命令、调用工具或写入文件，新的指令不一定会立即生效；已经完成的修改也不会因为一句补充要求自动消失。如果发现的只是小偏差，可以先追加一条明确的修正要求；如果已经出现明显错误方向、修改范围不断扩大，或者开始删除文件、替换技术栈和安装大量依赖，就应该直接中止当前任务。

中止只是让 Agent 不要继续执行，并不等于自动回退。停下来之后，首先要查看它已经修改了哪些文件、项目目前能否运行，以及哪些变化需要保留或撤销。确认现场之后，再决定让它局部修正、恢复到之前的版本，还是重新整理任务后再开始。

可以把判断原则压缩成一句话：小偏差就插话，方向错了就暂停；暂停以后先检查或者退回，不要立刻让 AI 接着乱改。

## 5.3 预览与验收

现在一些 Agent 已经具备比较完整的验收能力，可以启动网站、操作浏览器、点击页面、切换屏幕尺寸，甚至根据截图和运行结果继续修改。 但不同工具的能力并不一样，有时 AI 验收得比较慢，或者检查的只是它自己设定的几个项目，这时我们也可以直接接管浏览器，手动完成验收。

第一层当然是看网站最后呈现出来的结果。对于学设计的大家来说，一版就是把页面真正打开，在不同尺寸下点击和使用，是最直接也最必要的验收。（下一部分我们会具体讲 Dev Tool 怎么定位问题，怎么描述）

但在 Web 项目不断修改的过程中，我们也要偶尔回头看看源文件和修改差异。这里不要求大家马上读懂每一行代码，先观察几个明显信号就够了：AI 修改了哪些文件，有没有碰到与任务无关的配置，有没有突然安装很多依赖，原有内容是否被删除，以及某个文件是不是变得异常长。

所以验收至少有两层：一层检查“最后看起来和用起来是否正确”，另一层检查“AI 为了得到这个结果，究竟对项目做了什么”。界面正确，不代表项目结构一定健康；代码看起来整齐，也不代表最后的体验符合设计目标。两边都看，才算真正完成一次修改。

## 5.4 定位与修正错误（核心）

```resource
type: video
title: Chrome DevTools 浏览器调试工具精讲
url: https://www.bilibili.com/video/BV1KM4y1G7EF/
```

调试的目标，是找到“实际结果从哪一步开始偏离预期”。看到异常之后不要立刻连续修改代码，应先稳定地复现问题，并记录发生问题的页面、操作步骤、实际现象和预期结果。只有能够重复触发的问题，才容易判断一次修改是否真正有效。

### 先判断问题发生在哪一层

页面问题可以先按现象粗略分类。元素不存在或层级错误，优先检查 HTML 与组件结构；尺寸、位置、颜色异常，优先检查 CSS；点击后没有反应或内容变化错误，检查 JavaScript；图片、字体或远程数据没有出现，检查网络请求；刷新后状态异常或一直看到旧内容，检查本地存储与缓存；项目无法启动或发布，检查终端和构建日志；AI 修改后出现原本没有的问题，则同时检查文件差异。

可以把常用工具理解为一张“问题—证据”地图：

```diagram
结构与样式问题       → Elements、Styles、Computed
JavaScript 运行问题  → Console、Sources
图片与数据请求问题   → Network
缓存与本地状态问题   → Application
不同屏幕上的问题     → Device Toolbar
启动与构建问题       → Terminal
修改范围与回归问题   → 文件差异、版本历史
```

在 Chrome 页面中右键选择“检查”即可打开开发者工具。macOS 可以使用 `Command + Option + I` 打开开发者工具，使用 `Command + Option + C` 直接进入元素选择；Windows 和 Linux 可以使用 `Ctrl + Shift + I` 与 `Ctrl + Shift + C`。调试网络和初始化问题时，应先打开相应面板，再刷新页面或重新执行操作，否则可能错过问题发生时的记录。

### Elements：检查页面结构和样式

Elements 面板显示浏览器当前建立的 DOM 结构。使用选择元素工具点击页面中的对象，可以定位对应的 HTML 节点，并查看它实际匹配了哪些 CSS。Styles 显示样式来自哪个选择器和文件，被划掉的属性通常表示它被其他规则覆盖；Computed 显示浏览器经过继承、层叠和单位计算之后真正采用的最终值；盒模型则可以检查元素的宽高、内边距、边框和外边距。

可以在 Elements 中临时修改文字、类名和 CSS 数值，快速验证某个猜想。例如把 `display: none` 取消后内容重新出现，说明问题与显示规则有关。不过这些改动通常只存在于当前浏览器页面，刷新后会消失。确认方案后，仍然需要回到项目源文件中完成修改。

### Console：查看错误和检查运行状态

Console 会显示 JavaScript 错误、警告和程序主动输出的调试信息，也可以现场执行少量 JavaScript 来检查页面状态。遇到红色错误时，先阅读错误类型、错误信息、文件名和行号，再展开调用栈，观察错误经过哪些函数产生。一个早期错误可能导致后续功能连续失败，因此应先处理最早出现且能够对应当前操作的错误。

`console.log()` 可以帮助确认某段代码是否执行，以及变量在当时是什么值；`console.error()` 可以标记程序主动发现的异常。复制信息给 AI 时，应保留完整错误文本和最相关的调用栈，避免只截取“Error”一个词。不要在 Console 中粘贴来源不明的代码，也不要把令牌、Cookie 或个人信息发送给 AI。

### Network：查看浏览器请求了什么

Network 面板记录页面加载和操作过程中发出的请求，可以判断浏览器是否真的请求了某张图片、字体、接口或数据文件。调试时先打开 Network，再刷新页面或重新执行操作，然后观察请求地址、类型、状态码、耗时和文件大小。

状态码 `200` 通常表示请求成功，`304` 表示浏览器可以继续使用缓存内容，`404` 表示请求地址没有找到对应资源，`500` 一类状态通常表示服务器处理失败。点击一条请求后，可以在 Headers 中查看请求地址和参数，在 Payload 中查看提交了什么，在 Response 或 Preview 中查看服务器实际返回了什么，在 Timing 中观察时间主要消耗在哪一步。

请求失败时需要继续区分：页面根本没有发出请求，通常说明前端逻辑没有运行到该步骤；请求地址错误，可能是路径或数据字段的问题；请求成功但返回内容不符合预期，需要检查接口、数据和前端读取方式；返回正常但页面没有更新，则继续回到 Console 和组件状态中寻找原因。

### Sources：暂停 JavaScript 的执行过程

当 Console 只能告诉我们“哪里报错”，却不能解释变量为什么会变成当前值时，可以使用 Sources。断点会让 JavaScript 在指定位置暂停，此时可以查看局部变量、调用栈和表达式结果，再逐行执行代码，观察程序从哪个步骤开始偏离预期。

除了普通行断点，还可以在某次点击、网络请求或异常发生时暂停。初学阶段不需要记住所有按钮，只要掌握“找到相关文件—设置断点—重新触发问题—检查变量—逐步执行”这条基本路径。

### Device Toolbar：检查不同屏幕尺寸

Device Toolbar 可以模拟不同视口宽度、缩放比例、触控方式和网络条件，适合寻找响应式布局在什么宽度开始出错。不要只选择几个常见手机型号，还应该连续拖动视口宽度，观察导航、文字和图片在哪个临界位置发生挤压、溢出或错位。浏览器模拟不能完全替代真实手机测试，涉及字体渲染、触控手感和系统浏览器差异时仍需使用实际设备复查。

### Application：检查缓存和浏览器保存的数据

Application 面板可以查看 Cookie、Local Storage、Session Storage、缓存和 Service Worker 等浏览器端数据。当网站只在某台电脑上出现问题、退出后仍保留旧状态、更新后一直显示旧内容，或者登录状态异常时，可以在这里检查浏览器保存了什么。清除数据可以帮助验证问题是否由旧状态造成，但清除之前要确认其中没有需要保留的测试数据。

### Terminal：检查开发服务器和构建过程

浏览器展示的是网站运行到用户设备后的结果，终端则记录项目启动、编译、构建和服务器运行时发生的问题。项目无法启动、依赖缺失、文件导入失败、类型检查不通过或部署构建失败时，应先查看终端。重点寻找第一条明确的错误、关联文件和行号，并区分错误与普通警告；后面大量信息可能只是第一处失败引起的连锁反应。

### 文件差异：检查 AI 实际改了什么

调试 Vibe Coding 项目时，还要把运行证据与文件差异结合起来。文件差异可以回答哪些文件被修改、哪些内容被删除、是否意外更改了配置或依赖，以及问题是否从某次修改之后开始出现。先比较最后一个正常版本与当前版本，通常比让 AI 重新阅读整个项目更容易缩小范围。

一般现在的 Agent，都吸纳了 IDE 的显示，会显示具体改了哪些地方的代码。

### 一套完整的调试流程

1. 稳定复现问题，记录页面、设备、操作步骤、实际结果和预期结果。
2. 根据现象判断问题更接近结构样式、浏览器逻辑、网络数据、缓存状态还是构建运行。
3. 使用相应工具收集证据，先形成一个可以被证伪的原因假设。
4. 每次只做一项最小修改，避免同时改变多个变量。
5. 重新执行原来的复现步骤，确认问题消失。
6. 检查相邻页面、其他屏幕尺寸和相关功能，确认修复没有引入新的问题。

> [!example] 举例｜“加载更多”没有反应
> 可以先在 Console 查看是否出现 JavaScript 错误，再在 Network 中观察有没有发出数据请求。如果没有请求，并且 Console 指向点击处理函数，说明问题可能发生在请求发出之前；如果请求返回 `200` 但页面仍未更新，就需要比较 Response 中的数据结构与组件实际读取的字段。修正之后，再次点击按钮，确认请求成功、页面增加内容，并继续检查重复点击和移动端表现。

### 怎样把调试证据交给 AI

向 AI 求助时，应提供能够复现和判断问题的证据，包括发生问题的页面、操作步骤、预期与实际结果、Console 错误、失败请求的地址与状态码、终端错误以及最近的文件差异。先要求 AI 根据证据解释可能的原因和准备检查的文件，再执行小范围修改。

```prompt
在作品列表页点击“加载更多”后没有新增内容。预期每次增加 12 件作品；实际页面没有变化。Console 出现以下错误……；Network 中没有新的数据请求。请先判断错误发生在哪一步并说明证据，再进行最小范围修复。不要安装新依赖，修复后重新执行同一操作并报告验证结果。
```

## 5.5 代码质量或者说代码的组件化
代码质量听起来很像程序员的话题，但我们可以先用一个很直观的问题来判断：修改一个小地方，会不会牵动整个项目？
文件很长不一定有问题，但如果一个文件已经有几千行，同时包含页面内容、数据、样式和交互逻辑，它很可能已经变成所谓的“上帝文件”或者巨型文件。以后修改任何一个局部，都可能影响其他部分。遇到这种情况，可以先让 AI 解释这个文件承担了哪些职责、哪些内容存在重复、哪些部分适合拆分，再决定是否整理。不要只因为文件很长，就让它直接全部重写。
组件化是一种整理重复结构和公共规则的方法。比如课程卡片会在首页、课程列表和搜索结果中反复出现，就适合整理成一个组件；课程标题、时间和图片则作为数据传入。以后统一调整卡片样式，只需要修改这个组件，不必在每个页面中分别寻找。

组件也不是拆得越多越好。一个只出现一次、结构非常简单的标题，没有必要为了“组件化”单独建立文件。拆分的基本判断是：这部分是否有清楚的职责，是否会重复使用，是否需要独立修改和测试。拆得太少会形成巨型文件，拆得太碎也会让项目充满互相跳转的小文件。

前面讲过的数据、组件和页面，也可以用来检查项目架构。相关内容尽量放在一起，叫作“高内聚”；不同部分之间尽量减少不必要的依赖，叫作“低耦合”。修改一门课程的标题，最好只需要修改数据；统一改变课程卡片的图片比例，最好只修改组件；改变课程列表的排列方式，则主要修改页面。一次局部调整如果需要同时改动很多无关文件，通常说明项目结构已经耦合得比较紧。

可以先用自然语言让 AI 统计项目中超过 400 行的源代码文件，并说明每个文件分别承担了哪些职责。400 行只是一个方便排查的线索，不是判断代码好坏的统一标准；自动生成文件、依赖锁定文件和大段内容数据通常也不需要因此拆分。真正需要关注的是，一个文件是否同时混入了数据、页面结构、样式和多种交互逻辑，以及其中有没有大量重复内容。

可以类似直接这样问：

```prompt
先不要修改代码。统计项目中超过 400 行的手写源代码文件，排除自动生成文件、依赖锁定文件和内容数据。说明每个文件承担的职责、存在的重复逻辑、与其他文件的依赖关系，以及是否值得拆分。最后给出最小范围的整理建议，等我确认后再执行。
```

AI 可以帮助寻找拆分机会，但是否拆分仍要结合项目规模、修改频率和实际职责来判断。确认方案后再进行小范围重构，并检查页面内容和交互是否保持不变。

## 5.6 回退与恢复

在高风险修改之前保留可恢复的版本。如果结果不可接受，可以撤销局部修改、恢复上一个可靠版本，或者从保存的分支重新开始。恢复方式也应当作为任务约束提前告诉 AI。

如果不是很久远的历史，往往你也可以直接自然语言和 AI 沟通，让其退回到某一历史记录上。

## 5.7 密钥、依赖与安全边界

账户密码、访问令牌和 API 密钥不能直接写入公开代码或提交到仓库。安装新依赖、开放权限和连接外部服务之前，需要确认来源、用途和影响范围；涉及删除、覆盖或公开发布的操作，需要先确认准确目标。

# 六、GitHub、版本与团队协作

（这一块也是一个大板块，我已经在课程资源里放了一些 B 站上的介绍链接，大家可以在哪里面进一步了解。）

## 6.1 Git 与 GitHub


```resource
type: video
title: Git+Github核心概念大串讲
url: https://www.bilibili.com/video/BV1cGigBQE6n/
```


Git 是记录项目文件变化的版本控制工具，GitHub 是保存和协作管理 Git 仓库的平台。可以把 Git 理解为项目的版本历史机制，把 GitHub 理解为团队共享和在线协作的空间。


AI 可以帮助我们操作 Git 和 GitHub，例如克隆仓库、查看修改、创建提交和上传版本。不过它并不是凭空进入你的 GitHub 账户：电脑需要先安装 Git，涉及私人仓库或上传操作时，还需要通过浏览器、GitHub CLI 或 SSH 完成身份验证。AI 可以说明步骤并执行获得授权的命令，登录和权限确认仍然需要我们自己完成。

当我们要参与一个已有项目，或者使用 GitHub 上的开源项目时，通常先要进行 clone，也就是把远程仓库复制到本地电脑。可以这样告诉 AI：

```prompt
请把这个 GitHub 仓库克隆到当前目录。在执行之前先告诉我将要创建的文件夹名称，确认不会覆盖已有文件。克隆完成后阅读 README，说明项目怎样安装和运行，暂时不要安装依赖或修改代码。
```

克隆完成后，仓库会成为电脑上的一个项目文件夹。这个文件夹除了包含可以直接看到的代码和素材，还保存了 Git 版本历史以及它与 GitHub 远程仓库之间的关系。之后可以在本地修改和预览，通过 commit 保存阶段版本，再通过 push 把确认过的版本上传到 GitHub。


## 6.2 提交与版本历史

现在做 Git 提交，也不一定要自己记住和执行全部命令。可以先让 AI 阅读文件差异，按照修改目的整理这次更新，判断哪些内容应该放在同一个提交中，并为每个提交拟定清楚的说明。

不过，不要一上来就让它“把所有修改都提交”。项目中可能混有临时文件、密钥、构建结果，或者其他人尚未完成的修改。更稳妥的方式是先让 AI 只做分析：

```prompt
先不要提交和上传。检查当前文件差异，说明每项修改的目的，找出无关文件、临时文件和可能包含密钥的内容。按照“一次提交对应一个完整变化”的原则拟定提交计划，列出每次准备包含的文件和提交说明，等我确认后再执行。
```

确认提交计划之后，再让 AI 选择对应文件并创建 commit。一次提交最好对应一个能够说明和验证的阶段性变化，例如“完成课程卡片组件”“修复移动端导航”或“更新课程内容数据”，不要把视觉调整、依赖升级和无关内容修改全部混进同一个版本。

还要注意，commit 主要是在本地版本历史中保存一个节点，push 才是把这些提交上传到 GitHub。可以让 AI 创建提交但暂时不要上传，等本地预览和检查通过之后，再确认是否推送到远程仓库。

## 6.3 分支、合并与冲突

可以把 Git 的版本历史想象成一条不断向前延伸的路线，分支则是从某个可靠节点暂时岔出去的另一条路线。它允许我们在不直接影响正式版本的情况下开发新功能、修复问题或者尝试不同设计方案。

> [!example] 举例｜用分支修改移动端导航
> 课程网站当前稳定版本保存在 `main` 分支。我们准备重新设计移动端导航时，可以创建一个新的分支，只在其中进行修改和测试。如果结果不理想，正式版本不会受到影响；如果结果通过验收，再把这个分支合并回 `main`。

```diagram
main：稳定的课程网站
  └── feature/mobile-nav：修改移动端导航
                         ↓ 确认后合并
main：包含新版移动端导航
```

AI 可以帮助创建和切换分支，也可以在独立分支中完成修改。可以这样说明：

```prompt
请从当前稳定版本创建一个用于修改移动端导航的新分支。只修改导航相关文件，不要改动课程内容。完成后运行项目并列出文件差异，暂时不要合并到 main。
```

合并是把一条分支上的修改带回另一条分支。如果不同成员或多个智能体修改的是不同文件，或者同一文件中的不同位置，Git 通常能够自动合并；如果它们修改了同一段内容，并且 Git 无法判断应该保留哪一种结果，就会产生冲突。

冲突并不代表文件损坏，只表示 Git 需要人来做决定。处理时要理解两边分别想完成什么，再选择保留其中一边，或者把两边的有效内容重新组合起来。不要直接让 AI 无条件“接受当前版本”或“接受对方版本”，因为这样可能悄悄丢掉另一边的修改。冲突解决之后，还需要重新启动项目，检查页面、数据和交互是否能够一起正常工作。


## 6.4 在线预览与协作确认

代码仓库可以连接部署平台（第八章我们会讲），为每次提交或分支生成独立预览地址。团队可以直接查看实际页面，在确认内容、视觉和交互之后，再将修改发布到正式版本。

# 七、内容、数据与后台服务


## 7.1 先分清内容、数据、文件和操作

课程介绍和章节正文属于内容；课程名称、时间、教师和分类属于可以重复排列的数据；图片、视频和字体属于文件；登录、提交作业和保存进度则属于用户操作。它们可以出现在同一个网站中，却不一定适合保存在同一个地方。

先分清要处理的是什么，再决定使用 Markdown、表格、CMS、数据库还是对象存储。不要因为听说数据库比较“高级”，就把所有东西都塞进数据库。

## 7.2 最简单的方案：跟网站放在一起

对于本课程的大多数网站，最简单的方法是把内容直接保存在项目中。长篇文章可以使用 Markdown，重复的课程或作品信息可以使用 JSON，数量不多的图片也可以放在项目目录里。

这种方式容易理解，也可以跟随 Git 一起保存版本。缺点是每次修改内容通常都需要重新构建和发布，更适合内容数量有限、更新频率不高，并且主要由项目制作者维护的网站。

## 7.3 如果内容需要经常修改：文档、表格与 CMS

如果课程时间、作品信息或活动安排需要由多位老师和编辑持续更新，让所有人直接修改代码就不太现实。这时可以使用在线文档、表格或 CMS。

Google Docs 适合维护文章类内容，Google Sheets 适合维护字段比较固定的列表数据。CMS 则进一步提供专门的内容录入界面、分类关系、编辑权限、媒体管理和发布流程。网站需要通过构建脚本或接口读取这些内容，它们不会因为存在表格里就自动出现在页面上。

## 7.4 什么时候才需要数据库

当网站不只展示内容，还要持续记录用户行为时，数据库才真正变得重要。例如学生登录、提交作业、保存学习进度、收藏课程，或者教师需要按照班级、日期和状态查询记录。

数据库适合保存可以查询、筛选和关联的结构化记录。它带来的不只是“容量更大”，同时也增加了数据结构、权限、安全和备份等问题。因此，是否使用数据库取决于网站需要做什么，而不是网站看起来大不大。

## 7.5 图片和视频放在哪里：对象存储

对象存储主要用来保存图片、视频、音频和压缩包等体积较大的文件。数据库通常保存文件名称、作者、说明文字和访问地址，对象存储则保存文件本身。

> [!example] 举例｜作业记录与作业文件
> 一条作业记录可以保存在数据库中，其中记录学生、课程、提交时间和文件地址；真正的 PDF、视频或图片则保存在对象存储中。网页最后通过地址读取这些文件。

## 7.6 谁来处理用户操作：接口与后端函数

当用户提交表单、登录账户或读取受保护的数据时，网站需要有一段代码负责检查请求、执行规则和读写数据。浏览器不能安全地保存管理员密钥，也不应该毫无限制地直接操作数据库。

这些处理逻辑可以运行在传统云服务器上，也可以交给 Workers 等无服务器函数。后者按请求执行代码，因此这种情况下不需要先购买和维护一台长期运行的云服务器。（至于这些能力怎样部署到 ，第八章会继续详细讲）。

到了这里，顺便讲讲网站的上线方式粗略理解为三个方式。

静态资源托管，是把构建好的 HTML、CSS、JavaScript、图片和字体交给平台保存并发送给用户。课程介绍、章节内容和作品页面通常可以采用这种方式。网站仍然运行在平台的服务器和网络节点上，只是用户访问时不需要临时查询数据库并重新生成页面。

托管式服务端计算，是在用户登录、提交表单或读取数据时，通过 Workers、Functions 等服务运行一段后端代码。服务器依然存在，但平台负责基础设施、运行环境和扩展，我们只需要关注这段代码要处理什么请求，因此也常被称为 Serverless。

自行维护云服务器，则是购买一台长期运行的虚拟服务器，自己安装运行环境、配置网络、启动后端程序，并处理安全更新、日志、备份和故障。它提供更完整的控制，也带来更多维护工作。本课程的大多数项目通常不需要从这里开始。

## 7.7 回到我们的课程网站

这门课程最后制作的网站大多以内容展示为主，因此课程文章可以使用 Markdown，课程目录可以使用 JSON，少量图片可以随项目一起发布。只有当项目需要多人频繁更新内容时，才考虑在线表格或 CMS；需要登录、提交和长期保存用户记录时，再加入数据库与后端函数；图片和视频数量较大时，再使用对象存储。

# 八、网站发布与访问链路

## 8.1 本地、预览与正式环境

本地环境用于个人开发和调试，
预览环境用于团队确认某次修改，
正式环境面向真实用户。

三种环境可能使用不同的网址、配置和数据，发布前需要确认当前修改将进入哪个环境。

## 8.2 Vercel 与 Cloudflare

我们在本地完成的网站只是电脑里的一个项目文件夹，还不能被其他人通过互联网访问。自动部署平台可以连接 GitHub 仓库，当代码更新时，自动拉取代码、安装依赖、执行构建，再把生成的网站文件发布到互联网上。

Vercel 和 Cloudflare 这类就属于自动部署平台都可以完成这条流程。它们会替我们处理服务器、HTTPS、构建记录和版本发布，因此本课程通常不需要先购买和配置一台传统云服务器。

Vercel 更像一套围绕前端项目组织的网站制作与发布流水线。连接 GitHub 后，推送到生产分支会更新正式网站，推送到其他分支则可以生成独立预览地址。它的项目、部署、预览和团队协作界面比较直观，适合快速理解从代码修改到网站发布的完整过程。

Cloudflare 最初以 DNS、CDN、网络安全和全球节点见长，现在也可以连接代码仓库，自动构建并托管网站。通过 Workers 可以同时发布 HTML、CSS、JavaScript 等静态资源和少量服务端逻辑，再通过 D1、R2 等产品连接数据库和对象存储。Cloudflare Workers Static Assets

两者的能力存在大量重叠。Vercel 更强调以前端项目和团队预览为中心的发布体验，Cloudflare 更强调网站托管、服务端计算、数据存储、域名和全球网络之间的整合。这种区别主要帮助我们理解产品的使用重心，并不代表一种平台可以完全取代另一种。

这门课程建议使用 Cloudflare，是为了让大家在同一个平台中理解网站托管、Workers、D1、R2、域名和 CDN 之间的关系，同时减少课堂中切换平台的成本。


## 8.3 从代码仓库到自动部署

（现场 Cloudflare 为例，实际完成一次自动部署）：

选择 GitHub 仓库，确认项目目录，设置构建命令和输出目录，指定生产分支，再完成第一次发布。

连接完成后，平台会监听仓库变化。推送到生产分支通常会更新正式网站；推送到启用了预览构建的其他分支，则会生成独立预览地址。构建成功只表示平台顺利生成并发布了文件，还需要打开网站检查内容、图片、链接、交互和不同屏幕尺寸。

如果构建失败，不要只把“部署失败”四个字交给 AI。可以应该打开构建日志，找到最早出现的明确错误，把错误信息、构建命令、输出目录和相关配置一起提供给 AI，再进行小范围修正。

## 8.4 域名、DNS 与 HTTPS

网站第一次发布到 Cloudflare 后，平台通常会先分配一个地址，例如 Workers 使用的 项目名.账户名.workers.dev，或者 Pages 使用的 项目名.pages.dev。这个地址已经可以在互联网上公开访问，但它属于 Cloudflare 自有域名下面的子域名，名字较长，也不能脱离平台单独使用。课堂练习可以先使用这个地址，正式项目则可以进一步绑定自己的域名。

大家可以在域名注册商那里买，比如 Cloudflare、阿里云就可以买域名。

购买域名以后，网站并不会自动出现在这个域名中。还需要通过 DNS 记录告诉互联网：当用户访问这个域名时，应该去哪个平台寻找网站。可以把域名理解为网站的名字，DNS 负责登记这个名字所对应的服务位置，Cloudflare Workers 或 Pages 则负责实际提供网页文件和程序。

DNS 配置正确以后，部署平台还会为域名申请 HTTPS 证书。HTTPS 会加密浏览器与网站之间传输的数据，并帮助浏览器确认当前连接对应这个域名。使用 Cloudflare 绑定自定义域名时，相关 DNS 记录和证书通常由平台就自动创建了。

## 8.5 CDN 与缓存

> [!example] 举例｜不同地区访问同一网站
> 假设网站只存放在一台位于上海的服务器上，北京的用户访问可能很快，欧洲的用户则需要经过更长的网络路径。

CDN 中文称为内容分发网络，它会在不同地区设置边缘节点，将图片、字体、CSS、JavaScript 等常用资源缓存在距离用户较近的节点。后面的用户再次访问时，就可以直接取得附近保存的副本，不必每次都回到原始服务器，也就是“源站”。

缓存并不是永久保存。CDN 需要判断哪些内容可以缓存、缓存多长时间、内容更新后怎样清除旧版本，以及哪些登录、提交和实时查询请求仍然需要回到源站。这些规则合起来，可以理解为 CDN 配置。

# 九、网站优化与长期维护

## 9.1 图片、字体与代码体积

网站加载可以粗略理解为三个过程：浏览器先下载文件，再解析这些文件，最后执行其中的代码。文件越多、体积越大、相互依赖越复杂，用户等待的时间通常越长。性能优化首先要找到真正拖慢网站的资源，而不是凭感觉修改。

浏览器开发者工具中的 Network 面板可以显示页面加载了哪些文件、每个文件有多大、下载用了多久，以及哪些请求相互等待。Lighthouse 和 Performance 面板则可以帮助我们观察主要内容何时出现、页面什么时候可以顺畅操作，以及加载过程中是否发生布局跳动。测试时最好使用无痕窗口或关闭缓存，并模拟普通手机和较慢网络，否则本地电脑上的第二次访问往往会显得过于理想。

图片通常是最先需要检查的部分。一张最终只显示为 800 像素宽的图片，没有必要上传 6000 像素的原图。可以根据实际显示尺寸缩小图片，使用 WebP、AVIF 等适合网页的格式，并在视觉质量可以接受的范围内压缩。首屏最重要的主视觉应该优先加载，页面下方暂时看不到的图片可以延迟加载。为图片提前写明宽度和高度，还可以避免图片加载完成后把文字和按钮突然挤开。

字体文件也可能非常大。每增加一种字体、字重或斜体，浏览器通常都需要多下载一份文件。因此应先确认项目真正使用了哪些字体和字重，删除没有用到的版本，并优先使用适合网页的 WOFF2 格式。标题需要特殊字体时，可以只让标题使用，正文继续使用系统字体；中文字体包含大量字符，更要谨慎直接加载完整字库。

JavaScript 除了需要下载，还要经过解析和执行，过多时会让页面已经显示出来却暂时点不动。可以删除没有使用的代码和依赖，把暂时用不到的功能拆开，在用户打开相关页面或触发操作时再加载。一个简单效果没有必要安装体积很大的工具库，统计、地图、视频和聊天插件等第三方脚本也应按实际需求加载。CSS 同样可以删除重复和无效规则，并通过构建工具进行压缩。

部署平台通常会自动压缩文本文件，并通过 CDN 缓存图片、字体、CSS 和 JavaScript，但 CDN 无法消除文件本身过大、代码执行过多等问题。完成优化后，需要重新构建并再次测试，确认加载速度确实改善，同时检查图片质量、字体显示、交互功能和不同屏幕尺寸，避免为了提高一个性能分数破坏实际体验。

在 Vibe Coding 的工作过程中，可以先让 AI 只做检查，不要直接修改：

```prompt
请先不要修改代码。分析首页的构建产物和加载资源，按照文件体积和加载影响排序，说明哪些图片、字体、JavaScript、CSS 和第三方脚本最值得优化，并分别给出修改方案、可能节省的体积和修改风险。等我确认后再逐项处理。
```

## 9.2 响应式设计与可访问性
同一个网站可能出现在宽屏电脑、平板、手机上，也可能只是在电脑中被缩小了浏览器窗口。屏幕空间发生变化后，不能只是把整个电脑页面等比例缩小，还需要重新安排内容。比如三栏作品列表可以在手机上变成一栏，横向导航可以收起，字号、图片尺寸、段落宽度和按钮点击区域也需要随空间调整。这种根据可用空间改变页面布局和呈现方式的设计，称为响应式设计。

可访问性关注的范围更广：不同身体条件、使用环境和操作方式的人，能否感知、理解并操作网站。例如，用户能否只用键盘完成操作，文字与背景是否有足够的对比度，图片是否提供替代文本，表单错误是否说得清楚，HTML 是否具有合理的标题层级和语义结构。

简单来说，响应式设计主要解决“换一个屏幕还能不能正常看和操作”，可访问性进一步追问“换一种身体条件或操作方式还能不能使用”。两者共同构成网站的基本设计质量。

## 9.3 缓存更新与内容发布

内容或代码已经更新，但用户仍然看到旧版本时，问题可能出现在内容发布、代码提交、项目构建、CDN 缓存或浏览器缓存中的任何一环。排查时不要一上来就反复部署，而要先判断新内容究竟走到了哪一步。

可以先确认 CMS 内容是否已经发布、代码是否推送到了正确的生产分支，以及部署平台是否使用最新提交成功完成了构建。随后直接打开平台提供的默认域名，检查新版本是否已经上线。如果默认域名是新的，自定义域名仍然显示旧内容，问题通常更接近 CDN、DNS 或缓存层。

如果只有自己的浏览器看到旧版本，可以尝试强制刷新、使用无痕窗口，或者在开发者工具中暂时关闭缓存。如果不同设备都看到旧版本，可以检查 Cloudflare 的缓存状态，清除相关网址的 CDN 缓存，再重新访问。使用了 Service Worker 的网站还可能在设备本地保存完整页面，需要单独更新或注销。

长期来看，可以让 HTML 使用较短的缓存时间，让带有版本编号或内容哈希的图片、CSS 和 JavaScript 使用较长缓存。这样每次构建产生新的文件名，浏览器便会主动获取新文件，同时继续复用没有变化的旧资源。解决问题之后，还要沿着“内容来源—代码仓库—构建平台—CDN—浏览器”重新检查一次，确认新版本确实到达用户。

（这一部分也完全可以让 AI 帮你排查，留个印象即可）


## 9.4 监测、成本与备份

网站上线并不意味着工作结束。至少需要持续观察四类情况：部署有没有成功，用户访问时有没有报错，页面加载是否变慢，服务用量和费用有没有异常增长。

### 监测
最基础的监测可以形成一个固定节奏。每次发布后，先查看 Deployments，确认最新提交已经成功构建，再打开正式网站检查首页、主要页面、图片、链接和表单。构建失败时可以进入部署详情查看 Build log，找到最早出现的明确错误。

网站运行一段时间后，可以通过 Cloudflare Web Analytics 查看访问量、热门页面和真实用户的加载表现；如果项目使用了 Workers，还可以在项目的 Observability 中查看请求数量、错误、执行状态和日志。遇到用户反馈时，应记录具体时间、访问网址、操作步骤和报错现象，再根据相同时间段的日志寻找原因。[Cloudflare Web Analytics](https://developers.cloudflare.com/web-analytics/about/) 可以免费使用；[Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) 则会记录调用、错误和未捕获异常。

### 成本
费用监测主要看 Billing 中的 Billable Usage，同时分别查看 Workers、D1 和 R2 的用量。启用付费服务后，应该设置预算提醒，例如累计费用达到 5 美元或10美元时发送邮件。需要注意，预算提醒只负责通知，不会自动停止服务，所以收到提醒后仍然要检查是哪项服务产生了用量。[Cloudflare 费用监测文档](https://developers.cloudflare.com/billing/understand/usage-based-billing/)

> [!example] 举例｜课程网站的成本估算
> 在这门课中，大家制作的网站一般不会超出免费额度。使用 Cloudflare 默认域名时，托管成本通常可以保持为 0 元，因为静态资源请求目前免费且不限量。绑定自己的域名后，主要成本来自域名注册，普通域名可以先按照每年几十元到一百多元预留，具体价格取决于后缀、注册商和续费价格。[Workers 静态资源计费说明](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)
>
> 如果网站增加表单、搜索或动态接口，小规模课堂项目通常仍能使用免费额度。当前 Workers 免费计划允许每天 10 万次动态请求；D1 免费计划每天包含 500 万行读取、10 万行写入和总计 5GB 存储。需要升级时，Workers 付费计划的最低费用是每月 5 美元，大约可以按每月人民币三四十元估算。[Workers 限额](https://developers.cloudflare.com/workers/platform/limits/)、[Workers 价格](https://developers.cloudflare.com/workers/platform/pricing/)、[D1 价格](https://developers.cloudflare.com/d1/platform/pricing/)
>
> 如果使用 R2 保存用户上传的图片、音频或其他文件，当前每月包含 10GB 免费存储、100 万次写操作和 1000 万次读操作。超过后，标准存储价格为每 GB 每月 0.015 美元，此外还要计算操作次数。例如长期保存 50GB 文件，扣除免费额度后，单纯存储费用大约是每月 0.6 美元，实际账单还会受到读取和写入次数影响。[R2 价格](https://developers.cloudflare.com/r2/pricing/)


正式项目仍要在上线前重新查看价格页面。真正容易被忽略的成本还包括域名续费、CMS、邮件发送、第三方接口、AI 模型调用和团队协作工具，应该把所有外部服务一起列入项目成本表。

### 备份 
最后还要建立备份。代码应该保存在 Git 仓库中；CMS 和数据库需要定期导出；重要图片、视频和音频应在另一个位置保存副本；域名、DNS、环境变量和部署设置也要留下配置记录，但密钥不能直接提交到公开仓库。备份完成后还应尝试恢复一次，因为只有能够重新部署和恢复的数据，才算真正可用的备份。

## 9.5 隐私、版权与内容责任

发布网站之前，需要确认图片、字体、文本和用户数据的授权范围。涉及访问统计、表单、账户或个人信息时，还需要说明数据会被怎样收集、保存和使用。
